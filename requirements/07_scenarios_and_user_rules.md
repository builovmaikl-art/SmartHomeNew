Этот файл является модульным уточнением к разделу 7 файла `ТЗ обновлен.txt`.

Причина выноса: корневой файл ТЗ слишком крупный для надёжной точечной правки через текущий GitHub-agent режим, поэтому дальнейшие уточнения разделов допускается вести в отдельных файлах каталога `requirements/`.

## 7.1. Сценарии

- УТРО: освещение базовое 70%, акцентное 40%, ТП без коррекции, шторы открыты на 80%.
- ВЕЧЕР: освещение базовое 40%, акцентное 70%, ТП без коррекции, шторы закрыты на 90%.
- ОТЪЕЗД: три уровня согласно основному ТЗ, раздел 3.5.

## 7.2. Симуляция присутствия

- Активна только в режимах среднесрочного и долгосрочного отъезда.
- Интенсивность: 0.3 для среднесрочного, 0.2 для долгосрочного.
- Зоны симуляции: зоны освещения и группы розеток, кроме котельной, электрощитовой и технических помещений.
- Временные окна: утро 07:00–10:00, вечер 18:00–23:00, ночь 01:00–04:00 редко.
- Длительность события: случайная 5–45 минут.

## 7.3. Минимальная длительность сценария

- Минимальная длительность сценария: 5 минут.
- Изменение сценария до истечения 5 минут допускается только при подтверждении уровня доступа не ниже 4 или при аварийном/безопасностном приоритете.

## 7.4. Пользовательские правила «если — то»

### Назначение

Пользовательские правила позволяют задавать простую автоматику без перекомпиляции проекта.

Правила относятся к оперативно значимым настройкам и должны храниться в компактном конфигурационном хранилище. Они не являются журналом, историей или архивом.

### Минимальный пакет пользовательских правил в ПЛК

Минимальный пакет включает:

- конфигурационную модель одного правила;
- проверку одного условия;
- генерацию одного действия;
- публикацию действий в доменные менеджеры;
- сценарный rule-request через policy/scenario arbitration;
- preheat intent для отопления;
- приоритет rule-запросов ниже operator/gateway и ниже аварийных режимов.

### Модель правила

Правило описывается структурой:

```text
Enabled
Condition_Type
Condition_Target_ID
Condition_Op
Condition_Value
Condition_Value_Max
Action_Target_ID
Action_Value
Action_Type
Priority
```

### Поддерживаемые условия минимального пакета

- температура воздуха;
- температура пола;
- влажность;
- CO₂;
- CO;
- метан;
- дверь/окно;
- протечка;
- дым;
- движение;
- время суток;
- день недели.

### Поддерживаемые действия минимального пакета

- изменение уставок/команд ТП;
- включение/выключение освещения;
- включение/выключение розеток;
- управление вентиляцией;
- открытие/закрытие штор;
- активация сценариев;
- переключение света;
- переключение розетки.

### Приоритеты

Приоритеты должны соблюдаться в следующем порядке:

```text
аварийные режимы / safety
> operator/gateway-запросы
> rule-request
> стандартные сценарии / автоматические сценарные фоны
```

Если одновременно активно несколько rule-сценариев, выбирается активное правило с наибольшим `Priority`.

### Не входит в минимальный пакет

В минимальный пакет не входят:

- полноценные HMI-экраны визуального редактора правил;
- сложные группы условий AND/OR;
- импорт/экспорт правил;
- CSV-архивация правил;
- журнал истории срабатывания правил;
- расширенная диагностика конфликтов между правилами;
- календарные исключения;
- файловое хранение правил на USB/flash/SD.

Эти функции выполняются отдельными этапами после стабилизации логики и/или на этапе HMI/портирования.

### Реализованная привязка к текущему коду

Текущий минимальный пакет реализуется через существующий путь:

```text
G_HMI_User_Rules
→ FB_Rule_Engine
→ GVL_STATE.G_Rule_Actions
→ доменные менеджеры lighting/socket/heating
→ PRG_System_Scenario_Rules
→ GVL_POLICY.G_Rule_Preheat_Request
→ GVL_POLICY.G_Scenario_Request_Rule
→ FB_System_Scenario_Arbitration
```

Прямая запись пользовательских правил в физические выходы запрещена. Все действия проходят через соответствующие доменные менеджеры, policy/scenario arbitration или command arbitration.
