# Heating Diagnostics Gating Boundary Decision

Дата фиксации: 2026-04-23

## Вопрос
Следующий cleanup-этап по diagnostics / maintenance gating должен идти по какому пути:

1. ограничиться логической перегруппировкой внутри текущего `PRG_Heating.st`,
или
2. уже сейчас выносить diagnostics/gating в отдельный helper-layer.

## Контекст решения
После recovery и post-recovery ownership-аудита стало ясно, что diagnostics/gating cluster внутри `PRG_Heating` действительно перегружает wrapper. Но это само по себе еще не означает, что физический вынос в отдельный слой уже является лучшим первым шагом.

## Решение
На ближайшем cleanup-этапе **принимается решение сначала ограничиться логической перегруппировкой внутри текущего `PRG_Heating.st`**, без немедленного вынесения diagnostics/gating в отдельный helper-layer.

## Почему принято именно такое решение

### B-01. Сначала нужно сделать границы явными, а потом выносить
Сейчас проблема diagnostics/gating cluster не только в том, что он находится в одном файле с orchestration, но и в том, что внутри этого файла еще недостаточно явно разделены смысловые группы:
- diagnostics projection,
- maintenance gating,
- freeze-support logic,
- основной orchestration path.

Если сразу выносить код в helper-layer, высок риск просто перенести неочищенный смешанный кластер в новое место, не улучшив архитектуру по сути.

Вывод:
- сначала нужна смысловая перегруппировка,
- потом уже можно принимать решение о физическом выносе на чистой основе.

### B-02. `PRG_Heating` уже восстановлен и снова читаем как цельный wrapper
После recovery `PRG_Heating.st` снова стал цельным, непрерывным и пригодным для локальной структурной очистки.

Это означает, что следующий безопасный шаг — сначала сделать файл дисциплинированным по внутренним границам, а не дробить его преждевременно на новые единицы.

Вывод:
- у нас уже есть рабочая база для внутренней перегруппировки без нового recovery-риска.

### B-03. Ранний вынос helper-layer сейчас увеличит surface area изменений
Если уже сейчас вводить новый helper-layer, потребуется сразу решить:
- форму интерфейса helper-layer,
- ownership входов/выходов helper-layer,
- место вызова в orchestration order,
- границы публикаций в `GVL_STATE` и `GVL_STATUS`.

Это уже больше похоже на следующий архитектурный шаг, а не на локальный cleanup-этап.

Вывод:
- для текущего шага это слишком широкая поверхность изменений.

### B-04. Логическая перегруппировка даст более качественную основу для следующего решения
Если внутри `PRG_Heating` сначала появятся явные блоки:
- orchestration,
- diagnostics projection,
- maintenance gating,
- freeze hardware support,

то решение о helper-layer потом можно будет принимать уже по фактической структуре, а не по приблизительной картине.

Вывод:
- этот путь снижает риск ошибочного разрезания кода по неподходящей границе.

## Формальное boundary-решение
На текущем этапе фиксируется:

### Boundary decision
**Следующий cleanup выполняется как внутренняя логическая перегруппировка в рамках `PRG_Heating.st`.**

### Что это означает practically
Допустимо:
- перестраивать секции внутри `PRG_Heating.st`;
- отделять diagnostics publications от clamps;
- отделять freeze-support aggregation от общего diagnostics хвоста;
- делать код значительно более явным по внутренним границам.

Недопустимо без отдельного нового решения:
- вводить новый helper block / helper program layer;
- менять call order вокруг `PRG_Heating`;
- разводить новый интерфейсный контракт для diagnostics/gating слоя.

## Что НЕ означает это решение
Это решение не означает, что helper-layer никогда не понадобится.

Оно означает только следующее:
- helper-layer не является первым cleanup-шагом;
- сначала нужна чистая внутренняя граница;
- вопрос о физическом выносе будет пересмотрен после логической перегруппировки.

## Критерий успешности этого решения
Boundary decision считается успешным, если после следующего cleanup-шагa:
- `PRG_Heating` становится заметно более читаемым;
- внутри файла явно отделены orchestration, diagnostics, gating и freeze-support блоки;
- после такой перегруппировки можно уже уверенно сказать, нужен ли вообще отдельный helper-layer.
