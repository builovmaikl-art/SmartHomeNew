# Heating Post-Regroup Polish Execution Plan

Дата фиксации: 2026-04-23

## Назначение
Этот документ переводит `20_HEATING_POST_REGROUP_POLISH_PLAN.md` в **исполнительный порядок локальной полировки** `PRG_Heating.st`.

Это уже не общий план качества, а конкретная последовательность безопасных действий, которые улучшают читаемость файла без изменения логики, ownership и архитектурных границ.

## Основание
План опирается на:
- `18_HEATING_DIAGNOSTICS_GATING_REGROUP_RESULT.md`
- `19_HEATING_HELPER_LAYER_NEED_DECISION.md`
- `20_HEATING_POST_REGROUP_POLISH_PLAN.md`
- текущее состояние `PRG_Heating.st`

## Цель исполнения
Сделать `PRG_Heating.st` более аккуратным, единообразным и стабильным live-root source, сохранив:
- секции S1-S6;
- текущую логику;
- текущие ownership-решения;
- отсутствие helper-layer;
- текущие interfaces и call order.

## Execution Mode
- Режим исполнения: Direct Repository Modification Mode.
- Тип проверки: repository state verification.
- Ограничение: без утверждений о runtime-успехе до отдельной compile/run проверки.

## Зафиксированные инварианты перед изменением
Во время polish-этапа нельзя менять:
- owner для `GVL_STATE.G_Target_Temperature`;
- owner coarse heating intents в `PRG_Policy`;
- сигнатуры `FB_Heating_System_Manager.st`;
- сигнатуры `FB_DHW_Manager.st`;
- `MAIN.st`;
- any branch semantics, formulas, clamps or arbitration rules;
- boundary decision об отсутствии helper-layer на текущем этапе.

## Исполнительный порядок

### Шаг PPE-01. Нормализовать заголовки секций S1-S6
Действие:
- пройти все секционные комментарии;
- убедиться, что стиль заголовков единый по формулировкам, разделителям и капитализации;
- убрать возможные локальные несогласованности между секциями.

Ожидаемый результат:
- файл читается как единая дисциплинированная структура.

### Шаг PPE-02. Почистить локальные комментарии внутри S1-S2
Действие:
- пересмотреть старые комментарии вроде numbered-step пояснений (`// 9. ...`, `// 12. ...`) и другие локальные подписи;
- убрать или переписать те из них, которые хуже согласуются с новой секционной структурой;
- оставить только те комментарии, которые реально помогают читать orchestration-path.

Ожидаемый результат:
- верхний main-flow остается понятным, но без лишнего исторического шума.

### Шаг PPE-03. Выравнять стиль комментариев в S3-S5
Действие:
- проверить единообразие формулировок между diagnostics projection, maintenance gating и freeze support logic;
- убрать разношерстные подписи и фрагменты старого migration-tone;
- сделать подписи секций и подблоков краткими и согласованными.

Ожидаемый результат:
- diagnostics/gating tail читается как одна согласованная подсистема, а не как набор разноформатных хвостов.

### Шаг PPE-04. Уменьшить визуальный шум внутри секций
Действие:
- убрать лишние пустые строки и разрывы, если они не помогают чтению;
- сгруппировать близкие по смыслу строки компактнее, не меняя порядок вычислений и условий;
- сохранить при этом достаточную визуальную дистанцию между секциями.

Ожидаемый результат:
- файл становится плотнее и легче обозревается, но не превращается в трудночитаемую «стену текста».

### Шаг PPE-05. Проверить единый словарь терминов
Действие:
- пройти файл на согласованность терминов:
  - orchestration,
  - diagnostics projection,
  - maintenance gating,
  - freeze hardware support,
  - adapter copy-out;
- не смешивать близкие термины без причины.

Ожидаемый результат:
- внутри файла закрепляется устойчивый словарь, который совпадает с документацией этапа.

### Шаг PPE-06. Удалить остаточный migration-шум
Действие:
- проверить, не осталось ли комментариев или формулировок, звучащих как временные следы recovery/migration;
- удалить или переписать их, если они уже не несут актуальной ценности.

Ожидаемый результат:
- `PRG_Heating.st` выглядит как актуальный рабочий файл, а не как след переходного этапа.

### Шаг PPE-07. Выполнить repository-state verification после polish
Действие:
- перечитать итоговый `PRG_Heating.st` по состоянию репозитория.

Нужно подтвердить:
1. секции S1-S6 сохранены;
2. логика не менялась;
3. owner `G_Target_Temperature` не менялся;
4. interfaces manager blocks не менялись;
5. helper-layer не появился;
6. файл стал визуально чище и более единообразным.

Ожидаемый результат:
- локальная полировка подтверждена как безопасное non-functional улучшение.
