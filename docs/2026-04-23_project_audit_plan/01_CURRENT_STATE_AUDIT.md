# Current State Audit

Дата фиксации: 2026-04-23

## Контекст
Аудит выполнен по живому корню репозитория. Архивы, снимки, служебные отчеты и старые карты зависимостей использовались только как справочные следы и не принимались за источник истины.

## Краткий вывод
Архитектурный вектор проекта в целом правильный: система уже движется к централизованной схеме `Fault -> Health -> State -> Policy -> Actuation` с единым owner для системного режима и централизованной физической записью в `PRG_IO_Write`.

При этом корень репозитория все еще находится в переходном состоянии. Часть слоев уже выровнена, а часть остается незавершенной или содержит следы промежуточной миграции.

## Что уже выглядит правильно

### 1. Порядок вызовов в MAIN выровнен лучше, чем в старых аудитах
Текущий верхний контур уже разделяет:
- чтение IO,
- safety,
- system orchestration,
- policy,
- command arbitration,
- subsystem managers,
- physical IO write.

Это означает, что часть старых замечаний про неверный call order уже устарела и не должна переноситься в новые планы без повторной проверки по корню.

### 2. PRG_Safety стал intent-oriented
Safety-слой публикует safety intent и feed в health bridge вместо локального владения глобальным system mode.

### 3. PRG_IO_Write остается сильной частью архитектуры
Физическая запись в выходы централизована. Это надо сохранить как жесткий принцип и дальше не размывать ownership физических выходов.

## Зафиксированные актуальные проблемы

### A-001. Корневой PRG_Heating.st выглядит неполным
В текущем файле присутствуют текстовые вставки вида:
- `... (same code omitted for brevity until thermal block, unchanged)`
- `rest unchanged`

Для живого runtime-файла это недопустимо. Требуется отдельная проверка:
- поврежден ли корневой файл,
- был ли в корень записан сокращенный вариант,
- или проект сознательно хранит в корне неисполняемый сокращенный фрагмент.

Приоритет: CRITICAL.

### A-002. Interface mismatch между PRG_Security и FB_Access_Control
`FB_Access_Control` требует вход `VI_System_Mode`, но в `PRG_Security` этот вход не передается при вызове `fbAccessControl(...)`.

До отдельной compile-проверки это фиксируется как вероятная интерфейсная несостыковка высокого приоритета.

Приоритет: HIGH.

### A-003. Command layer migration не завершен
В проекте уже существует shadow-слой команд:
- `PRG_Command_Arbitration` заполняет `GVL_COMMAND_SHADOW`,
- `PRG_IO_Write` использует shadow-команды для физических выходов,
- `PRG_Ventilation` читает operational requests из shadow-команд.

Но при этом:
- комментарии в `GVL_COMMAND_SHADOW.gvl` противоречат текущему использованию,
- `PRG_Command_Verifier` сверяет legacy layer и shadow layer как будто миграция еще не завершена,
- часть ветвей arbitration пустая и не реализует ожидаемое действие.

Приоритет: CRITICAL.

### A-004. PRG_Command_Verifier может залипать в аварийном состоянии
В текущем коде mismatch-флаг активируется при расхождении, но не видно явного симметричного сброса активного состояния при возврате к совпадению.

Это нужно проверить и при подтверждении исправить.

Приоритет: HIGH.

### A-005. Пустой цикл для water-zone arbitration
В `PRG_Command_Arbitration` есть цикл по `I_Water_Zone_Close_Required[1..32]`, который фактически ничего не делает.

Это выглядит как незавершенный участок migration/work-in-progress.

Приоритет: HIGH.

### A-006. PRG_System остается слишком перегруженным
Сейчас в одном program-layer смешаны:
- timekeeping,
- redundancy,
- recovery,
- health/state,
- HMI/status,
- fault logging,
- evacuation logic,
- scenario/gateway bridges,
- side effects в config/status слоях.

Даже если логика корректна, размер и количество ролей в одном orchestration-блоке увеличивают риск регрессий и усложняют поддержку.

Приоритет: HIGH.

### A-007. Подсистемные FB слишком тесно связаны с глобалами
`FB_Heating_System_Manager` и `FB_Ventilation_System_Manager` не только потребляют policy/system mode, но и напрямую пишут в глобальные признаки деградации в `GVL_STATE`.

Это ослабляет границы ownership, ухудшает тестируемость и делает subsystem code менее изолированным.

Приоритет: MEDIUM-HIGH.

### A-008. Актуальные live-файлы и вспомогательные карты/аудиты разошлись
Устарели или уже частично не соответствуют корню:
- некоторые старые `AUDIT_*`,
- `workspace/reachable_graph_from_main.md`,
- `workspace/dependency_map_live_root.md`,
- отдельные миграционные комментарии в GVL и program layers.

Это повышает риск того, что следующие изменения будут опираться на неверную картину проекта.

Приоритет: HIGH.

## Что не считать проблемой без дополнительной проверки

### N-001. Старые выводы о неправильном call order
Эти выводы нельзя автоматически переносить в новый план. Текущий `MAIN.st` уже перестроен.

### N-002. Старые замечания про broken motion source в PRG_Security
По текущему корню motion-массив уже заполняется из `GVL_STATE.G_Motion_Sensors`, а не сам из себя.

## Главный рабочий вывод
Новый цикл работ должен идти не от старых архивных аудитов, а от текущего корня. Основные приоритеты сейчас:
1. проверить и восстановить heating cluster как живой runtime-контур,
2. дожать command-layer migration до непротиворечивого состояния,
3. выровнять interfaces и ownership между system / safety / security / access,
4. только после этого обновлять карты зависимостей и итоговую документацию.
