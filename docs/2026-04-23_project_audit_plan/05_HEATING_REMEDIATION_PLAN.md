# Heating Remediation Plan

Дата фиксации: 2026-04-23

## Основание для плана
План построен на выводе из `04_HEATING_CLUSTER_AUDIT.md`: в текущем живом корне основной риск heating cluster связан прежде всего с нарушенной целостностью `PRG_Heating.st`, а не с отсутствием доменной heating logic как таковой.

## Цель
Восстановить heating cluster до состояния, в котором:
- `PRG_Heating.st` подтвержден как целостный live-root source,
- heating wrapper можно безопасно анализировать и менять,
- связь `PRG_Heating -> FB_Heating_System_Manager -> FB_DHW_Manager -> state/outputs` становится прозрачной,
- последующие доработки делаются уже на подтвержденном program-layer, а не на поврежденном или сокращенном placeholder.

## Основной принцип
До восстановления целостного `PRG_Heating.st` запрещается считать heating cluster готовым к точечному функциональному рефакторингу.

То есть ближайший этап — не optimization, не cleanup отдельных формул и не тюнинг алгоритмов отопления, а именно восстановление и подтверждение целостности orchestration-layer.

## Область работ
- `PRG_Heating.st`
- при необходимости связанные live-root вызовы heating в `MAIN.st`
- интерфейсные связи с `FB_Heating_System_Manager.st`
- интерфейсные связи с `FB_DHW_Manager.st`
- связанные global publications в `GVL_STATE`, `GVL_STATUS`, `GVL_COMMAND`

## Запрещенные действия до завершения этапа восстановления

### Z-001
Не выполнять локальные логические правки внутри середины `PRG_Heating.st`, пока не подтвержден полный живой текст файла.

### Z-002
Не принимать snapshots и archive-варианты как автоматический источник восстановления без отдельного сравнения с live root.

### Z-003
Не менять heating policy semantics (`NORMAL / DEGRADED / FREEZE_PROTECTION / SAFE_STOP`) до подтверждения program-layer.

### Z-004
Не обновлять итоговую heating documentation как будто cluster уже подтвержден, пока не завершен этап восстановления.

## План работ

### Шаг H-R1. Подтвердить статус текущего `PRG_Heating.st`
Задача:
- формально зафиксировать, что корневой файл действительно хранится как сокращенный/placeholder-like текст,
- подтвердить, что это не артефакт отображения одного инструмента,
- проверить, нет ли в корне второго актуального heating wrapper под другим именем.

Результат шага:
- отдельная короткая фиксация, что live-root heating wrapper действительно нецелостен.

Критерий завершения:
- нет разумных сомнений, что проблема относится к реальному корневому источнику, а не только к отображению.

### Шаг H-R2. Найти ближайший кандидат на полный heating wrapper
Задача:
- найти наиболее вероятный полный текст `PRG_Heating.st` среди связанных артефактов,
- сравнить кандидата с текущими интерфейсами `FB_Heating_System_Manager.st`, `FB_DHW_Manager.st` и вызовами из `MAIN.st`,
- не переносить файл автоматически, а сначала зафиксировать происхождение кандидата.

Источники сравнения допускаются:
- snapshots,
- связанные служебные следы,
- предыдущие корневые версии,
- вспомогательные экспортные материалы.

Результат шага:
- один основной кандидат на восстановление,
- при необходимости один резервный кандидат,
- краткая таблица различий относительно текущего live root.

Критерий завершения:
- выбран один базовый кандидат, который лучше всего согласуется с текущими live-root интерфейсами.

### Шаг H-R3. Проверить совместимость кандидата с текущим live root
Задача:
- сверить сигнатуры вызовов heating/DHW FB,
- проверить используемые глобалы и side effects,
- проверить, не опирается ли кандидат на уже удаленные или переименованные поля,
- проверить, не возвращает ли он проект в более старую архитектуру ownership.

Результат шага:
- список требуемых адаптаций до безопасного возврата файла в корень.

Критерий завершения:
- подготовлен явный список обязательных адаптаций, без которых восстановление нельзя делать.

### Шаг H-R4. Восстановить целостный `PRG_Heating.st` в live root
Задача:
- заменить сокращенный placeholder-like program-layer на целостный текст,
- сохранить текущий архитектурный вектор проекта,
- не вносить лишние функциональные изменения сверх необходимых для восстановления.

Результат шага:
- в корне лежит единый непрерывный `PRG_Heating.st` без текстовых вставок `omitted for brevity` / `rest unchanged`.

Критерий завершения:
- файл в корне выглядит как полноценный живой source и пригоден для дальнейшего детального анализа.

### Шаг H-R5. Выполнить post-recovery ownership audit heating wrapper
Задача:
- уже на восстановленном `PRG_Heating.st` пройти цепочку сверху вниз и снизу вверх,
- определить реальные writers/readers,
- выделить, какие публикации в глобалы допустимы, а какие стоит выносить или стандартизировать.

Результат шага:
- отдельный ownership audit heating wrapper.

Критерий завершения:
- прозрачная карта heating cluster ownership после восстановления.

### Шаг H-R6. Только после этого переходить к functional cleanup
Задача:
- разбирать качество логики heating/DHW,
- обсуждать cleanup прямых записей в globals,
- уточнять policy contract,
- убирать архитектурный шум и дублирование.

Результат шага:
- cluster становится готов к нормальному рефакторингу без работы на сломанной основе.

## Риски

### R-001. Ложное восстановление из старого snapshot
Самый опасный риск — вернуть в корень старый heating wrapper, который формально полный, но архитектурно уже не соответствует текущему live root.

### R-002. Смешение восстановления и рефакторинга
Если одновременно восстанавливать файл и менять логику, будет трудно понять, что относится к repair, а что к redesign.

### R-003. Невидимый rollback ownership
Старый кандидат может вернуть старые ownership-паттерны, которые уже были вычищены в других подсистемах.

### R-004. Ложное чувство завершенности
Даже после восстановления полного `PRG_Heating.st` heating cluster еще не считается очищенным — это только допуск к следующему полноценному аудиту.

## Критерии успеха этапа remediation
Этап считается успешно завершенным, если одновременно выполнены все условия:

1. В live root существует полный `PRG_Heating.st` без placeholder-вставок.
2. Восстановленный файл согласуется с текущим `MAIN.st`.
3. Восстановленный файл согласуется с текущими интерфейсами `FB_Heating_System_Manager.st` и `FB_DHW_Manager.st`.
4. Не обнаружено явного возврата к старому ownership-конфликту.
5. После восстановления можно отдельно документировать heating wrapper ownership без догадок о пропущенных кусках.
